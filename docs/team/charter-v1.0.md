## 1. 团队价值观

我们不只写下来，我们照着做。五条，按优先级排列：

1. **可运行优先于完美。** 任何一天结束时，`main` 必须能构建、能启动。宁可少一个功能，不要一个跑不起来的分支。
2. **说清楚再动手。** 任务开做前，承接人要能用一句话复述「做完什么样」。复述不出来，说明需求没拆清，回去问 PO。
3. **代码是给队友看的。** 评审时看不懂的命名、跳不过去的逻辑、没有测试的分支，都是缺陷，不是风格问题。
4. **问题当天暴露。** 卡住超过 2 小时必须在群里说，不许拖到站会。报阻塞不丢人，藏着捂出问题才算失误。
5. **承诺要兑现。** Sprint 承诺的故事就是欠团队的债；完不成要在 Review 上讲清楚，不接受「默默没做完」。

**我们不做的**：不在 `main` 上直推；不合并没有测试的 PR；不在 Sprint 中途塞新需求；不用「大概好了」作为完成标准。

## 2. 沟通约定

### 2.1 渠道与用途

| 渠道 | 用途 | 响应时限 |
| --- | --- | --- |
| 微信群「CampusOverflow 冲刺群」 | 日常同步、求助、阻塞上报 | 工作时段 2 小时内 |
| GitHub PR / Issue 评论 | 技术讨论、评审意见、决策留痕 | 24 小时内 |
| 每周实验课（2 学时） | 站会、评审、回顾、结对 | 现场 |
| 电话 | **仅**用于线上环境故障、CI 全红等紧急事件 | 立即 |

### 2.2 硬规则

- **技术结论必须落到 PR 评论或文档。** 微信里聊定的方案，由当事人补一条 PR 评论或 ADR，否则视作未决策。
- **@ 到人，不 @ 全体。** 提问时写清「背景 / 我已试过 / 卡在哪 / 需要谁做什么」。
- **阻塞上报格式**：`【阻塞】<一句话> | 卡了多久 | 已尝试 | 需要谁`。
- **非工作时段**（23:00–08:00）不发非紧急消息；确有紧急事项在标题前加 `[URGENT]`。
- 有分歧时先各写 3 行理由，再投票；**技术分歧 30 分钟内没结论，由 SM 指定一人拍板并记入 ADR**，不再拖延。

### 2.3 会议节奏

| 会议 | 频率 | 时长 | 主持 | 产出 |
| --- | --- | --- | --- | --- |
| Daily Standup | 每周实验日 + 冲刺周隔日 | ≤ 15 min | SM | `docs/team/standup-<日期>.md` |
| Sprint Planning | 每 Sprint 开始 | 30 min | PO | Sprint Backlog |
| Sprint Review | 每 Sprint 结束 | 每队 5 min | PO | 演示录屏 + 反馈清单 |
| Retrospective | 每 Sprint 结束 | 25 min | SM | `docs/retro/sprint-<n>.md` |

站会三问不变：昨天做了什么 / 今天要做什么 / 有什么阻塞。**站会上不解决技术细节**，会后单独拉相关的人。

## 3. 开发规约

### 3.1 分支策略（GitHub Flow 简化版）

```
main（受保护，永不直推）
 ├─ feature/<拼音>-<简述>    新功能
 ├─ fix/<拼音>-<简述>        缺陷修复
 ├─ docs/<拼音>-<简述>       文档
 └─ lab/<编号>-<简述>        实验单元
```

- 分支从 `main` 切出，生命周期 **≤ 3 天**；超过 3 天的分支要在站会说明。
- 推送前先 `git fetch && git rebase origin/main`，保持线性。
- 合并方式：**Squash and merge**，`main` 上一条 PR 一个提交。
- PR 合并后删除远程分支。

### 3.2 提交信息（约定式提交）

```
<type>(<scope>): <中文简述>

[可选的正文：为什么这么改]

Refs: #<issue>
Signed-off-by: 姓名 <邮箱>
```

`type` 取值：`feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `ci`。
示例：`feat(qa): Question 聚合新增投票不变式校验`。

### 3.3 代码与评审

- **评审时限**：PR 提出后 24 小时内必须有人响应；超过 48 小时无人响应，SM 直接指派。
- **评审规模**：单个 PR **≤ 400 行**；超过则拆分。文档类 PR 不受此限。
- **审批数**：Sprint 0–1 需 **1 个 LGTM**；Sprint 2 起 **2 个**（且不得是作者本人）。
- **LGTM 含义**：我读过、我理解、我认可，出了问题一起担。只写「LGTM」不写理由的，**视为无效**。
- 评审意见分级：`[必须改]` / `[建议改]` / `[仅讨论]`。带 `[必须改]` 的 PR 不能合并。
- **作者自己合并自己的 PR 是被禁止的**（分支保护已强制）。

### 3.4 技术规约

| 领域 | 约定 |
| --- | --- |
| 后端 | JDK 21 + Spring Boot 3.x，DDD 四层分包（domain / application / infrastructure / interface），按限界上下文物理分模块 |
| 聚合 | Setter 私有化，用工厂方法与聚合方法保护不变式，禁止贫血模型 |
| 数据库 | MySQL 8 + Flyway 迁移，脚本命名 `V<n>__<描述>.sql`，**禁止手工改库** |
| 前端 | React 18 + TypeScript 5 严格模式，禁用 `any`；服务器状态用 TanStack Query，客户端状态用 Zustand |
| 配置 | 所有密钥与地址走环境变量 / Secrets，**禁止硬编码进代码或 Dockerfile** |
| 日志 | Logback 输出 JSON 结构化日志，禁止 `System.out.println` |
| 接口 | 变更须同步 `docs/api/openapi.yaml`，前端类型由它生成 |

## 4. DoD 初版（Definition of Done v1.0）

> 一条用户故事只有在**全部满足**以下条目时，才能从 In Review 移到 Done。
> Sprint 1 末尾回顾会可修订此清单。

**代码与构建**

- [ ] 代码已合并进 `main`，且 `main` 可成功构建
- [ ] 分支命名符合 §3.1，提交信息符合 §3.2
- [ ] 单个 PR ≤ 400 行，且只做一件事

**质量**

- [ ] 核心逻辑有单元测试，本地测试套件全绿
- [ ] 前端 `pnpm lint` 与 `pnpm typecheck` 无新增告警（无新增 `any`）
- [ ] 已按 Gherkin 验收标准逐条手工验证：快乐路径、边界路径、异常路径

**流程**

- [ ] 获得规定数量的有效 LGTM（含理由），`[必须改]` 意见已全部处理
- [ ] CI 状态检查 `build` / `lint` / `test` 全绿
- [ ] 涉及的接口变更已同步 `openapi.yaml`
- [ ] 涉及重要设计决策的，已提交 ADR

**可演示**

- [ ] PO 已在实际环境（本地或测试服）看过功能运行，并确认符合验收标准
- [ ] 无硬编码密钥、无调试输出、无临时文件混入

> Lab 7 起在 CI 中加入质量门禁（覆盖率 > 70%、Bugs = 0、Vulnerabilities = 0），届时未达标的 PR 自动拦截。

## 5. 角色与决策

| 事项 | 决定权 |
| --- | --- |
| Backlog 内容与优先级 | PO |
| Sprint 承诺范围 | 团队（PO 提出，全员同意） |
| 技术方案选型 | 提出者写 ADR，团队评审，SM 拍板 |
| 流程与 DoD 执行 | SM |
| 是否允许合并 | reviewers（受分支保护强制） |

角色在每个 **Sprint 末尾投票轮换**，每人 4 个 Sprint 内至少担任 1 次非 Developer 角色。
首次轮换：Sprint 1 末尾（第 4 周）。
