# 基线 CI 状态说明（Sprint 0）

> 结论先行：**`main` 的 CI 现在是红的，而且这是预期的。** 不是谁写错了代码，是基线框架里的
> 107 个 `TODO(Sx)` 方法还没实现。请看完全文再决定要不要救红灯。

## 1. 实测状态（2026-10-22，`main` @ f13f5b7）

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| 后端 · 编译 | ✅ success | `mvn compile` 通过，基线的类结构是完整的 |
| 后端 · 单元测试 | ❌ **failure** | 领域层测试跑起来后打在 `TODO(Sx)` 占位实现上，必然失败 |
| 后端 · 架构约束检查（ArchUnit） | ⏭ skipped | 上一步失败导致跳过 |

对应 Actions 记录：`CI · run #1`，作业 `后端构建与验证` 在第 5 步「单元测试」失败。

## 2. 为什么会这样

`docs/学生任务清单.md` 写得很清楚：共 **107 个待实现方法，分布在 32 个文件**，每个都带 `TODO(Sx)` 标记。
基线只提供骨架 + 测试，实现要学生填。所以：

- **测试是真的需求说明书。** 先读测试，再写实现，让它变绿。
- **在 S2/S3 的方法填完之前，后端测试不可能全绿。** 这是课程设计，不是团队失误。

## 3. 对 Lab 1 的影响与处理

**影响**：所有 PR 的「后端构建与验证」都会显示红叉，包括只改文档的 PR（如 PR #3 / #5）。
如果现在就开「CI 必绿才能合并」的分支保护，全队一个 PR 都合不了，Sprint 0 会被直接堵死。

**处理**（已在章程 §4 DoD 中体现，此处再明确一次）：

| 阶段 | 合并门禁 | 理由 |
| --- | --- | --- |
| Sprint 0–1（现在） | **不把后端测试设为必须通过**；文档类 PR 由评审人确认「未触碰 `backend/`」即可合并 | 基线测试天然红，门禁会把流程卡死 |
| Sprint 2 起 | 把「单元测试」加为必须通过的 status check | 届时 S2 的领域方法应已填完，测试具备转绿条件 |
| Lab 7 | 加覆盖率门禁（>70%）、Bugs = 0 | 与课程实验 7 对齐 |

> 分支保护配置时，`Require status checks` 只勾选 **`前端构建`**（当前是绿的）；
> 「后端构建与验证」等 Sprint 2 再勾。这一点务必和组长对齐，否则第一个 PR 就过不去。

## 4. 谁该做什么

- **全体**：跑一次 `cd backend && mvn -q -DskipTests compile` 确认本地能编译（这个应该是绿的）。
- **后端主力**：按 `docs/学生任务清单.md` 的顺序，从 S2 的 `Question` / `Answer` / `Vote` 领域方法入手。
- **QA（朱淦）**：在 Sprint 2 Planning 上重新评估「测试转绿」的可行性，别把不现实的承诺写进 Sprint Backlog。
- **PO**：确认「Sprint 2 起测试必须绿」这个时间点是否可实现，必要时顺延到 Sprint 3。
