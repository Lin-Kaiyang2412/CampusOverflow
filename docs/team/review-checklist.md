## 0. 先说清楚：这份清单不是什么

**不是打勾表。** 一个 5 行的 CI 配置和一個 400 行的领域实现，用同一套标准逐条过是浪费时间。

正确用法是先看改动属于哪一类，再决定重点查什么：

| 改动类型 | 重点查 | 可以跳过 |
| --- | --- | --- |
| 领域层（聚合/值对象） | 不变式、状态机守卫、错误码 | 性能、SQL |
| 应用层（Service） | 事务边界、权限判定、异常处理 | 命名风格 |
| 基础设施（Repository/Adapter） | **SQL 是否下推过滤**、N+1、迁移脚本兼容性 | 业务逻辑 |
| 接口层（Controller） | 入参校验、HTTP 语义、暴露面 | 领域规则 |
| CI / 部署配置 | 触发条件、凭据是否外泄、失败会不会误伤 | 业务逻辑 |
| 纯文档 | 与代码是否一致 | 以上全部 |

## 1. 正确性（Correctness）

- [ ] **状态转移有没有守卫**：每个改变状态的方法，是否拒绝非法起始状态？
  > 实例：#31 `CourseMember.approve()` 里的 `requirePending()`。没有它，已处理的申请可以被重复审批。
- [ ] **边界值处理**：空集合、null、`0`、负数、超长字符串。
- [ ] **异常路径的错误码是否符合 `docs/错误码.md` 分段约定**（1xxx 业务规则 / 2xxx 冲突 / 3xxx 权限 / 4xxx 未找到，带 `QA-`/`REP-`/`DIS-`/`ID-` 前缀）。
  > 一个错误码不要承载两种语义——#31 里 `ID-1014` 同时表示「只有被拒绝的申请可重新提交」和「待审核不能调整角色」，前端按码分支会误判。
- [ ] **并发与幂等**：两个请求同时进来会怎样？重复提交会怎样？
- [ ] **数据库迁移是否兼容既有数据**：加非空列必须有 DEFAULT；改列要考虑历史行。
  > 实例：#31 的 `ADD COLUMN status ... DEFAULT 'APPROVED'`，让既有成员自动成为正式成员，不回退。
- [ ] **有没有偷偷放大 PR 范围**：标题写「前端 ESLint」，里面却改了后端 JDBC 配置。
  > 实例：#21。这类混搭会让 `git blame` 严重误导后来的人。

## 2. 可读性（Readability）

- [ ] 方法/变量命名能否自解释，不需要读实现才懂。
- [ ] 复杂条件判断有没有提取成有名字的布尔变量或私有方法。
- [ ] 注释写的是**为什么**而不是**做了什么**（后者代码本身已经说了）。
- [ ] 错误提示文案是人话，且能指导用户下一步做什么。
  > 「你已加入该课程」比「选课申请冲突」有用。

## 3. 可测性（Testability）

- [ ] **新增分支有没有对应测试**。
- [ ] 测试是在验证**行为**还是验证**实现**？断言 `status == PENDING` 是行为，断言 `mock 被调用了 1 次` 是实现。
- [ ] 测试有没有走过场：只构造对象然后 `assertThat(x).isNotNull()` 不算测试。
  > 反例对照：#31 的 `IdentityExpansionServiceTest` 用 `stored[0]` 模拟持久化，真的跑了一遍 PENDING→APPROVED 流转并验证期间对外不可见，这才算数。
- [ ] 领域层逻辑是否**不依赖 Spring 容器**即可测试（纯单元测试）。
- [ ] 涉及真实数据库的走 Testcontainers，不要靠 mock Repository 冒充集成测试。

## 4. 安全（Security）

- [ ] **有没有硬编码密钥/密码**：配置里只能出现 `${ENV_VAR}`。
  > 重点看 `application.yml`、`docker-compose.yml`、`sonar-project.properties`、CI workflow。
- [ ] **Actuator / 管理端点暴露面**：对外只应暴露 `/actuator/health`，其余不代理出去。
  > 实例：#32 的 nginx 只代理了 `/actuator/health`，这条做得对。
- [ ] **监听地址**：本地调试配置应绑 `127.0.0.1`，不要 `0.0.0.0` 把实例暴露到局域网。
- [ ] 是否越权：操作人校验是「查了角色」还是「查了角色**且**状态合法」？
  > #31 的 `requireCourseManager` 要求 `isApproved() && role().canManage()`，待审成员拿不到审核权。
- [ ] 用户输入展示处是否转义（防 XSS）；SQL 是否参数绑定（防注入）。

## 5. 性能（Performance）

- [ ] **过滤条件是否下推到 SQL**，不是全表捞出来在应用层 filter。
  > 实例：#31 用 `findByCourseIdAndStatus(courseId, "APPROVED")` 派生查询，而不是 `findByCourseId` 再内存过滤。
- [ ] 循环里有没有查数据库（N+1）。批量场景应先 `findAllById` 再 map。
  > #31 的 `pendingApplications` 用 `users.findAllById(...)` 一次性取，正确。
- [ ] 新增查询有没有对应索引支撑？
  > #31 加了 `idx_member_course_status (course_id, status)`。
- [ ] 事务边界是否只在应用层，有没有把大查询包进事务。

## 6. 风格（Style）

> **以下各项已由自动化覆盖，人工不必重复查**：见 §7。

- [ ] 分层依赖方向正确：domain 不依赖 infrastructure/interfaces（ArchUnit 已卡）。
- [ ] 聚合根用私有构造 + 工厂方法，不直接 new。
- [ ] 提交信息符合约定式提交，带 `Signed-off-by`。

## 8. 硬性阻断项（发现即打回，不商量）

1. 改动了 `backend/` 代码却声称「只改文档」。
2. 新增分支零测试覆盖，且理由只是「来不及」。
3. 配置里出现明文密钥。
4. 领域层出现对 infrastructure 的依赖。
5. 为了通过门禁而调低阈值或加 `@SuppressWarnings` 掩盖问题。

## 9. 评审意见的写法

一条合格的评审意见包含三要素：**在哪 → 有什么问题 → 为什么是问题**。

```
❌ 这里写得不好
✅ CourseRepositoryAdapter:58 用裸字符串 "APPROVED" 查询，
   拼错不会报错、只会静默返回空列表。建议改用
   CourseMemberStatus.APPROVED.name()，让编译期就能发现。
```

如果只是建议而非阻断，标明「非阻塞」——作者可以选择后续处理，PR 不必因此卡住。
