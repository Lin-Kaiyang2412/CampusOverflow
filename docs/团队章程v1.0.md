## 4. Git 协作规范

- **分支模型（GitHub Flow）**：main 为受保护分支，禁止直接提交；所有改动经功能分支 + PR 合入
- **分支命名**：`feature/模块名`（新功能）、`fix/问题描述`（修复）、`hotfix/问题描述`（紧急修复）、`docs/主题`（文档）
- **提交信息前缀**：`feat:` / `fix:` / `docs:` / `refactor:` / `chore:`，建议带 scope，如 `feat(question): add create question API`
- **GitHub Flow PR 流程**：
  1. 从最新 main 切分支：`git checkout -b feature/xxx`
  2. 本地开发并自测（单测 / lint / typecheck 通过）
  3. push 分支，创建 PR 并**关联 Issue**
  4. 至少 1 人 review approve 后合并（Squash merge）
  5. 合并后删除远程分支，本地同步 main
- 文档入库：章程、Backlog、ADR、术语表、运维手册等一律以 Markdown 提交入库

## 5. PR 审查制度

- 每个 PR 必须关联 Issue（Lab 任务或 Bug），标题说明变更内容
- **至少 1 名非作者 reviewer approve 后方可合并；作者不得自审自批**
- 评审关注：功能正确性、测试覆盖、代码风格、安全与性能隐患、是否遗留 TODO/调试代码
- 阻塞性问题（Blocking）未解决禁止合并；普通意见须 resolve conversation 后再合
- 合并方式：Squash merge，合并即删除源分支
- 评审清单（reviewer 逐项勾选）：实现符合验收标准 / 有对应测试且通过 / 无遗留 TODO / CI 全绿 / 无敏感信息泄露

## 6. 会议与同步制度

- **每日站会**：每次实验课前 10 分钟，每人汇报：做了什么 / 要做什么 / 阻塞点（SM 主持）
- **周会**：每周五课后 15 分钟，同步 Sprint 进度、风险与依赖（SM 主持，PO 补充优先级变化）
- **Sprint Review**：Sprint 末尾，PO 主导演示可运行增量，对照 Sprint Backlog 逐项验收
- **Sprint Retrospective**：Review 后进行，记录：做得好的 / 待改进的 / 下 Sprint 改进项
- 会议纪要入库：`docs/meetings/` 下以日期命名的 Markdown 提交

## 7. 完成定义（DoD）

一个任务/故事满足以下**全部**条件才算完成：

- [ ] 功能实现符合 Issue 描述与验收标准（对应 Gherkin 场景通过）
- [ ] 相关单元测试已编写且通过（`mvn test` / 前端测试）
- [ ] CI 流水线全绿（GitHub Actions）
- [ ] 代码评审通过（≥1 人 approve，无未解决阻塞意见）
- [ ] 涉及文档已同步（API 文档 / ADR / 术语表）
- [ ] 无硬编码密钥、无个人敏感信息

## 8. 代码质量门禁

- 后端：`mvn clean install` 全绿；JaCoCo 领域层覆盖率 ≥70%（核心聚合 ≥90%，S4 提至 80%）；ArchUnit 全通过
- 前端：`pnpm lint` + `pnpm typecheck` 全绿；pre-commit 钩子（Husky）生效
- CI：GitHub Actions 每次 push 自动构建；测试失败或覆盖率不达标的 PR 视为未通过 review，不得合并
- 敏感信息：禁止提交 `.env`、密钥、令牌；误提交须立即从历史中移除

## 9. 版本与发布

- 基线版本 v0.1.0（Sprint 0）
- 每个 Sprint 结束打版本标签（如 v0.2.0、v0.3.0...），合并完成后在 Releases 发布
- 发布前置：DoD 全部满足、演示通过、运维手册与部署配置入库
